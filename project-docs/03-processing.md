# 03 - Real-Time Stream Processing & Enrichment

## 1. Spark Structured Streaming & Runtime Topology

The data processing layer is powered by **Apache Spark Structured Streaming** running on a Kubernetes cluster managed by the **Spark Operator**. In Structured Streaming, data streams are treated as unbounded, continuously growing tables. Spark processes incoming micro-batches with end-to-end fault tolerance, checkpointing, and exactly-once processing guarantees.

### Decoupled Runtime Topology
Rather than submitting all jobs to a shared Spark driver context (which creates a single point of failure and makes resource management difficult), the system implements a decoupled runtime topology:
*   **Dedicated Driver Containers:** Each streaming job runs as an independent Kubernetes deployment. The driver container manages the streaming query, coordinates task distribution, and handles failure boundaries for its specific job.
*   **Isolated Checkpoint Directories:** Streaming checkpoint directories (stored in persistent volumes) are scoped per job. This allows jobs to recover independently from their exact offset state without impacting other queries.
*   **Scale-Out Executors:** Spark workers spawn executor pods dynamically to handle parallel micro-batch computations, coordinating with the Spark Master.

## 2. Dimension Materialization Streaming Job

To enrich raw news articles with contextual metadata (such as the source domain, publishing company, and country of origin) without query-blocking the database, the system implements a **Dimension Materialization Job** (`phase3-dimension-materializer`).

```
┌───────────────────────┐
│  Dimension CDC Topics │
│  (Links, Country, etc)│
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│   Spark Streaming     │
│   Materializer Job    │
└──────────┬────────────┘
           │ Idempotent Postgres Upsert
           ▼
┌───────────────────────┐
│ PostgreSQL Dim Tables │
│  (Curated Dimensions) │
└───────────────────────┘
```

### Reference Data Processing
Rather than querying the raw Postgres tables on every article event, Spark Structured Streaming processes raw CDC events from the reference topics:
*   `table_links`, `table_authority`, `table_pays`, `table_rubrique`, `table_langue`, `table_sedition`.

It normalizes their schemas, filters out unused fields, and materializes them into optimized PostgreSQL dimension tables:
*   `phase3_dim_links`, `phase3_dim_authorities`, `phase3_dim_countries`, `phase3_dim_rubrics`, `phase3_dim_languages`, `phase3_dim_seditions`.

These curated tables are indexed by their dimension IDs and serve as a low-latency join layer for the article processor.

## 3. Canonical Article Processor

The core processing engine is the `phase3-canonical-article-processor` PySpark streaming application. It executes the core ingestion-to-canonical workflow.

### Enrichment and Late-Arriving Dimensions
When a raw news record is consumed, Spark performs a streaming-to-relational lookup against the curated PostgreSQL dimension tables.
*   **Country Resolution Strategy:** The country is resolved using a hierarchical lookup:
    1.  Primary: `authority.sedition_id -> sedition.pays_id -> pays` (providing the physical publishing country).
    2.  Fallback: `links.pays_id` (providing the target country associated with the link).
*   **Dimension Status Resolution:** If key dimensions are missing due to network delays or late-arriving CDC records, the processor assigns a `dimension_status`:
    *   `complete`: All required and optional dimensions resolved.
    *   `partial`: Optional dimensions missing, but core fields resolved.
    *   `pending_required`: Core fields (such as source news ID or title) missing. The record is held in a retry queue.
*   **Minimum Feed Gate:** Articles are emitted as canonical articles once minimum fields (`title`, `url`, `published_at`, `is_visible`) are valid, even if the classification is still pending.

### Text Cleaning & Excerpt Generation
*   **HTML & Whitespace Stripping:** Raw body text is cleaned of HTML tags, scripts, and duplicate formatting characters to yield `body_text_clean`.
*   **Deterministic Excerpt:** An `excerpt` is generated by grabbing precisely the first 30 cleaned words from the article body. This serves as the display text on feed cards and provides the textual context for embedding classification.

## 4. Centralized Embedding Gateway

To obtain text vectors from LLMs or embedding providers without overloading APIs or violating rate limits, the system exposes a centralized internal **Embedding Gateway** service.

*   **API Isolation:** Isolates API keys and endpoints (e.g. `https://integrate.api.nvidia.com/v1`) from the Spark execution workers.
*   **NVIDIA BGE-M3 Configuration:** The gateway is configured for the `baai/bge-m3` model, returning a dense 3584-dimension vector.
*   **Global Rate Limiting:** Enforces a strict budget of **40 requests per minute (RPM)**. 
*   **Batching & Queueing:** Accumulates individual embedding requests into batches of up to **8191 tokens** before dispatching them to maximize throughput.
*   **Resiliency & Backoff:** If a `429` (Too Many Requests) or `5xx` error occurs, the gateway handles retries using exponential backoff.
*   **Batch Splitting:** If a large batch repeatedly fails, the gateway splits it into smaller sub-batches to isolate bad inputs and prevent overall pipeline blockages.
*   **Local Fallback (llama.cpp):** If the external provider is completely unreachable, the gateway falls back to a local `llama-cpp` deployment serving the `Gemma-2B` embedding model (`embeddinggemma-300M-Q8_0.gguf`) running in the cluster.

## 5. Topic Taxonomy & Embedding Refresh

The platform categorizes articles into a business-defined topic hierarchy.

### Taxonomy Schema
The **Topic Taxonomy** is stored in the database (`imperium_topic_taxonomy` / `phase3_topic_taxonomy`) and contains:
*   `topic_id`, `parent_topic_id`, `display_name`, `description`, `tags`, `embedding_seeds`, `signals` (strong, medium, weak), and `dimensions` (events, actors, impact areas).

### Topic Embedding Refresh Job
To map articles to these topics, the platform precomputes and stores a vector representation for each topic. A Kubernetes Batch Job (`refresh-topic-embeddings-job`) runs whenever the taxonomy changes:
1.  **Synthesize Topic Description:** For each category, it builds a descriptive text block combining display name, descriptions, tags, seeds, signals, and context:
    ```
    Topic: Politics & Government
    Description: Government, elections, public policy, diplomacy, and political institutions.
    Embedding seeds: government policy...; elections parliament...
    Strong signals: elections, government, parliament...
    Key events: election, policy decision...
    ```
2.  **Request Embeddings:** The job calls the local `llama-cpp` service (or NVIDIA API) to generate the vector embedding for the combined text block.
3.  **Durable Storage:** The resulting vectors are stored in `imperium_topic_embeddings` along with metadata like the `embedding_model` and `taxonomy_version`.

## 6. Embedding Similarity Classifier

Once the article embedding and topic vectors are available, the `phase3-article-classifier` job handles primary classification:

```
                  ┌──────────────────────────────┐
                  │ Cleaned Article Context      │
                  │ (Title + First 30 Words)     │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                         [central gateway] ──> NVIDIA BGE-M3 (3584-dim)
                                 │
                                 ▼
                  ┌──────────────────────────────┐
                  │      Article Vector          │
                  └──────────────┬───────────────┘
                                 │
                                 ├─ Cosine Similarity comparison
                                 │
                  ┌──────────────▼───────────────┐
                  │ Broadcasted Topic Embeddings │
                  │ (Precomputed in PostgreSQL)  │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                     Primary Topic (Leaf)
```

### Classification Execution
1.  **Broadcasting Topic Vectors:** Spark loads the precomputed active topic embeddings from PostgreSQL and broadcasts them to all execution worker nodes.
2.  **Cosine Similarity:** For each incoming canonical article event, Spark calculates the cosine similarity between the article's vector ($\vec{A}$) and each topic's vector ($\vec{T}$):
    $$\text{Similarity} = \frac{\vec{A} \cdot \vec{T}}{\|\vec{A}\| \|\vec{T}\|}$$
3.  **Assign Topic:** The topic with the highest similarity score is assigned as the article's **Primary Topic**.
4.  **Taxonomy Resolution:** The processor looks up the primary topic in the local taxonomy hierarchy to identify its top-level **Root Topic** (which is used for Redis feed indexing).
5.  **Output Event:** Spark updates the canonical article fields (`primary_topic_id`, `root_topic_id`, `topic_confidence`, `classification_status = classified`) and publishes the updated record back to Kafka.
